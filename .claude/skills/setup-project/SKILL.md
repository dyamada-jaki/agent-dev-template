# プロジェクトの準備をする

テンプレートから作ったばかりのリポジトリを、PO と開発チームが動ける状態にする。終わると、この端末がそのまま PO になる。
**準備は「制作の環境」と「開発プロセス」の両方。** 依頼が制作の環境の話だけ（例: 「PowerPoint と PDF で出したいのでセットアップして」）でも、プロセスの準備まで行う。

- このスキルの本体は `.claude/skills/setup-project/`。Codex 用の `.agents/skills/setup-project` はこのフォルダへのシンボリックリンクなので、直すのはここだけでよい
- Orca で開いた、main の worktree（リポジトリの元のフォルダ）の端末で動かす。`ORCA_TERMINAL_HANDLE` が無い、または別の worktree にいるなら、止めて人間に「Orca で main の worktree の端末を開き直して」と伝える
- 以下の `orca` は `/Applications/Orca.app/Contents/Resources/bin/orca`（`ORCA_CLI_BIN_DIR` があればその中）。PATH 上の同名コマンドが使えるとは仮定しない
- 途中まで済んでいるリポジトリでも使える。手順1の点検で × の項目だけを行う
- 分からない値は推測で埋めず、人間に聞く。人間にしかできないこと（有料アプリの導入・ログイン・社内資料の入手など）は、一覧にして頼む

## 1. 点検する
- `bash .claude/skills/dual-implement/scripts/dev-team.sh doctor` を実行し、× と △ の項目を控える
- 人間の最初の依頼を控える。手順2の材料になる

## 2. 作るものを決める（CLAUDE.md・AGENTS.md・testing.md）
CLAUDE.md の `<…>` が残っていれば行う。
- 人間の依頼から、作るものの種類・使う人と場面・出力の形式・使う道具・守るデザインや決まりを読み取る。足りない点だけを、次の「モデルの質問」とまとめて1回で聞く
- **モデルの質問**: 「開発設定」の表の「〜のモデル」の行（PO・起動係・開発チーム・実装する開発者・レビュー・後片付け）を、今の値を「おすすめ」として並べ、変えたいものがあるか聞く。選択肢を出せる道具（AskUserQuestion など）があれば使う
  - 開発チームは、エージェント（Claude Code か Codex）も聞く。Codex は「試験中」と添える
  - PO のモデルは、今のこの端末には効かない。次に PO を開き直すときから使う
  - 後片付けのモデルは Claude Code の開発チームのときだけ効く。Codex の開発チームを選んだら聞かない
  - 答えは表の行に書く。「開発チームのモデル」は `エージェント` / `モデル` / `effort` の3つを `…` で囲む形を崩さない（`dev-team.sh` が読む）
  - 後片付けのモデルを変えたら、`.claude/skills/finish-issue/SKILL.md` の先頭の `model`・`effort` も同じ値にする
  - モデルの名前が分からないとき（新しい名前を言われたなど）は、推測で書かず人間に確かめる
- `profiles/README.md` を読み、合う種類があればその値を使う。無ければ同じ README の「新しい種類を足す」に従って値を決める
- CLAUDE.md の次を埋める・直す。リポジトリは `gh repo view --json nameWithOwner` の値にする
  - 冒頭の説明、「作るもの」、「コマンド」、「ディレクトリ構成」
  - 「開発設定」の表: 確認コマンド・テスト先行・E2E・ミューテーション・開発サーバー・ポート・画面確認の幅。使わない項目は「なし」
  - 開発サーバーは、ポートを指定して起動し、そのポートが使われていたら止まる書き方にする（Vite なら `--port <ポート> --strictPort`）。Docker を使わないと `.env` の `HOST_PORT` は読まれないので、worktree ごとにポートを分けるにはコマンドで渡す必要がある
  - 「守ること」の 1・4・9・10（設計の決まり、言語、公開してはいけない情報、文章の決まり）と「用語」
- 終わったら `cp CLAUDE.md AGENTS.md` で同じ内容にする
- Web アプリ以外なら、`docs/testing.md` の確かめ方（主に2章）を作るものに合わせて書き換える
- `docs/definition-of-done.md`（完了の定義）を作るものに合わせて直す。要らない項目は消し、種類に要る項目を足す（例は `profiles/README.md`）
- 仕様の元になる資料（デザインシステム・設定資料など）があれば、場所と扱い（読むだけ・公開してよいか）を CLAUDE.md の「守ること」に書く

## 3. 制作の環境を整える
- 「開発設定」の確認コマンドが動くように、道具と雛形を用意する（例: Web アプリなら `package.json` と `.nvmrc`、スライドなら出力のツールと書体）
- 確認コマンドを実際に実行して通す。通らない項目は、理由と、人間に頼むことを控える
- 依存パッケージを足したら、理由を控えて手順8で人間に見せる

## 4. CI を置く
`.github/workflows/` に CI が無ければ行う。
- 確認コマンドを回す CI を `.github/workflows/ci.yml` に置く。Web アプリなら `profiles/web-app/ci.yml` をコピーする
- GitHub の CI で動かせない道具（PowerPoint など）は、CI では回せる確認だけにする。CI で回さない確認は「開発設定」の確認コマンドの欄にそう書く

## 5. GitHub を整える
- ラベル: `gh label create 開発可 --force` と `gh label create 着手中 --force`（名前は「開発設定」の「着手のラベル」）
- マージ: `gh repo edit --enable-squash-merge`

## 6. この端末を PO として登録する
- `docs/workflow.md`「PO を開く」の3つのコマンドを実行し、すべて通ることを確かめる。2つ目の `dev-team.sh po-register` で、この端末が PO になる
- Codex の素の `codex` で動いていて `.git` への書き込みや `gh` が失敗したら、止めて人間に「Orca からエージェントとして Codex を起動し直して」と伝える

## 7. 起動係を作る
点検で「起動係の定期実行がある」が × なら作る。「有効」だけが × なら、作らずに有効にするだけでよい。「自分の端末を閉じる」だけが × なら、作り直さずに、点検が示すコマンドで指示文を `docs/workflow.md` の形に直す。
- `docs/workflow.md`「開発チームを開く」の作り方で作る。名前は `開発チーム起動（<リポジトリ名>）`、`--workspace` はこのリポジトリの main の worktree の絶対パス、`--extra-agent-args` は「起動係のモデル」にする。ほかのプロジェクトの定期実行は変えない
- 作るときは `--disabled` のままにし、手順8で人間に有効にしてよいか聞く。5分おきに確認するが、「開発可」の Issue が無いあいだはエージェントを起動しない（費用はかからない）

## 8. 人間に見せて、コミットする
- もう一度 `dev-team.sh doctor` を実行する。人間に頼む項目と、有効にする前の起動係を除いて × が残っていれば、手順に戻って直す。× を残したまま終わりにしない
- 人間に次を見せる
  - 点検の結果（○ / × / △）
  - 変えたファイルと要点（埋めた「作るもの」と「開発設定」、セッションごとのモデル、足した依存パッケージと理由）
  - 起動係を有効にしてよいか。答えが「よい」なら `orca automations edit --id <ID> --enabled` を実行し、点検をもう一度通す
  - 人間に頼むことの一覧
- 人間の確認を受けてから、変えたファイルを main にコミットして push する（エージェントの土台は人間が確かめてから置く）

## 9. PO として始める
- `docs/workflow.md` の「3つの席」と「最初に1回だけやる準備」、CLAUDE.md（Codex では AGENTS.md）の「PO の席でのやり方」を読み、ここから PO として振る舞う。作るものは自分で作らず、決まったら Issue にする
- 人間に「次は、作るものについて話しながら `docs/spec.md` の初版を作ります」と伝え、最初の依頼の内容から議論を始める
